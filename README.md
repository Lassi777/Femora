# FEMORA — Personalized Menstrual Care (Prototype)

A fully functional, responsive React + Vite prototype for **FEMORA**, a venture
concept for biodegradable sanitary pads with a personalized recommendation
system. Built for an entrepreneurship project — every page, button, and flow
works end to end, using local state and `localStorage` (no backend, no payments).

> ⚠️ This is a demonstration prototype. Recommendations are generated by a
> transparent, rule-based engine (not a trained AI model) and are explicitly
> labeled as non-medical. See `src/services/recommendationEngine.js`.

---

## 1. Installation & running locally

Requires [Node.js](https://nodejs.org) 18+.

```bash
cd femora
npm install
npm run dev
```

Then open the URL Vite prints (usually **http://localhost:5173**).

To build a production bundle:

```bash
npm run build
npm run preview   # serves the built app locally
```

## 4. How the recommendation logic works

Located in `src/services/recommendationEngine.js`. Two entry points:

- **`computeFromAnswers(answers)`** — used when the user completes the
  10-question flow. Maps flow level to a base pad size, then adjusts for
  heaviest-flow day, night-time use, leakage concern, skin sensitivity,
  irritation frequency, comfort importance, odor concern, and preferred
  length.
- **`computeFromProblemText(text, tags)`** — used for the "I have a
  problem" path. Runs simple keyword matching (e.g. "heavy", "leakage",
  "rash", "sensitive", "odor", "night", "comfort", "sweat", "light")
  against the free-text description and any quick-select tags.

Both return the same shape: `{ size, flowLevel, absorbency, thickness,
softness, leakageProtection, skinFriendly, skinFriendlyPriority,
odorManagement, material, reasons, ... }`. The `reasons` array is shown on
the Recommendation page under "Why this configuration?" so the logic stays
transparent to the user.

**Conflict priority** (highest first), matching the design brief:
1. Safety / skin sensitivity
2. Flow & absorbency
3. Leakage protection
4. Comfort
5. Sustainability
6. Other preferences

### Changing the logic
- **Pad catalog / pricing** — edit `PAD_CATALOG` at the top of
  `recommendationEngine.js` (label, thickness, softness, price, tagline).
- **Questionnaire questions/options** — edit the `QUESTIONS` array in
  `src/pages/Questionnaire.jsx`.
- **Flow → size mapping** — edit `FLOW_TO_SIZE` in the engine file.
- **Keyword rules for the free-text path** — edit `KEYWORD_RULES` (each
  entry is a list of trigger words plus an `effect(recommendation)`
  function that mutates the draft recommendation).
- **Quick-select problem tags** — edit the `TAGS` array in
  `src/pages/ProblemInput.jsx`.

## 5. Period tracker

Visible on the Home page (and summarized on the Dashboard) once a person is
logged in. It's a simple calendar-based estimate — not a medical
prediction — implemented in `src/services/periodTracker.js`:

- The user enters their **last period start date** and an **average cycle
  length** (defaults to 28 days, allowed range 20–45).
- `computeNextPeriod(lastPeriodDateStr, cycleLength)` adds the cycle length
  to the last period date to project the next one, and returns how many
  days away that is (or how overdue it is).
- The entry is saved per logged-in user (`periodTracker` in
  `UserContext`) and clears when a different person logs in, consistent
  with how the rest of the personalization data is scoped per user.

## 8. Accounts, admin and order tracking (v2)

- **Sign up / Log in** (`src/pages/Auth.jsx`): customers create an account (name, email, phone, age, password) and log in. Passwords are stored hashed.
- **Admin login**: choose the *Admin* tab on the login page. Credentials live (hashed) in `src/config.js`.
- **Admin dashboard** (`/admin`): total orders, in-progress, delivered, customers, revenue; searchable/filterable order list with full customer + delivery details; change any order's status; add a note for the customer; customer list; CSV export.
- **Customer dashboard**: "My Orders" shows each order with a status timeline (Placed → Confirmed → Packed → Shipped → Out for Delivery → Delivered), admin notes, and a Cancel button until the order is packed.
- **Data storage**: browser `localStorage` (accounts, orders, per-customer progress). Open tabs sync live. For use across different devices, the storage layer in `src/context/UserContext.jsx` must be replaced by a real backend/database.


## 9. Demo vs production (important)

This is a **demo**. Accounts, orders and profiles live in browser `localStorage`; the admin login and password hashing run in the browser. This is **not secure authentication**: anyone with access to the browser can read or edit the data. "Orders" are demo records only - no purchase, payment or delivery happens, and "demo revenue" is not real sales. A production version needs a server with server-side auth (e.g. bcrypt/argon2 hashing), access control on customer/order data, and an updated privacy policy.

## 10. Recommendation engine

`src/services/recommendationEngine.js` is deterministic and rule-based (not AI, not medical advice); the conflict rules are listed at the top of the file. Free text is matched by whole words, negation reaches back up to 4 words and stops at words like "at", "but", "and" (so "no leakage at night" negates leakage only), "slightly" never means light flow, sweating is noted but changes nothing (no sweating-specific feature exists), and discomfort/comfort have separate negation handling. Both routes return the same shape and each reason describes a rule that fired. Size tiers bundle length and absorbency (an illustrative design choice); a larger tier means more coverage, not guaranteed absorbency or leak prevention. Specs and prices are illustrative (`CATALOG_NOTE`).

## 12. v6: product-type-correct recommendations, real 3D viewer, locked cancellations

- **Product types** (`src/services/products.js`): one catalogue for pads (existing 4 sizes), tampons (Regular/Super/Super Plus), menstrual cups (Small/Medium/Large) and period underwear (Light/Moderate/Heavy/Overnight). `recommendProduct()` only ever returns a variation of the chosen type; pads still use the existing, unchanged pad engine. "Not sure yet" opens a neutral comparison and requires choosing a category. Changing the product type clears the old recommendation and pack. Prices are proposed prototype values.
- **Trusted totals**: pack validation and totals always come from the catalogue (`validatePack`, `packTotals`); orders store type, variation lines, count and total, and the order store rejects wrong-type items or bad quantities.
- **3D viewer** (`src/components/viewer/`): real WebGL via three.js (lazy-loaded), original procedural geometry for a pad, tampon, cup and period underwear, image-based lighting, soft ground shadow, orbit drag (vertical page scroll still works on touch), arrow-key rotation, pauses off-screen, respects reduced motion, and falls back to a static labelled illustration if WebGL is unavailable. It is a concept render, not a product photo.
- **Cancelled orders are locked** (`src/services/orderStore.js`): every mutation re-reads stored orders and applies a rule; a cancelled order rejects any status change or note, repeated cancellation is a no-op, and only the owner can cancel an eligible order (Placed or Confirmed). The admin UI shows a "Locked" state with no dropdown. This is browser-side logic, not server-enforced security.
- **Homepage**: hero redesigned without illustration or prices; the old "range" cards with pad drawings and per-pad prices were replaced by a text overview of the four product types. Prices remain on the recommendation, pack builder, summary and order pages.
- Tests: `npm test` runs engine, product, order-rule and UI-source tests (49).

## 13. Checkout and payment methods (v7)

Flow (in `src/pages/Summary.jsx`): review pack -> delivery address (validated) -> payment method -> confirmation.

- Payment step: **Online Payment** (then choose **UPI** or **Credit/Debit Card**) or **Cash on Delivery**. Nothing is preselected; COD never shows the online sub-options; the button stays disabled until a valid choice exists.
- The order is created only at the end of the payment step. The checkout keeps one order id, repeat submissions return the same order (`addOrderInStorage` is idempotent), and the pack is cleared once it becomes an order.
- Orders store `paymentMethod` (`COD` | `UPI` | `CARD`), `paymentStatus` (always `PENDING` here), `paymentMode: 'demo'`, plus the existing order status. Payment status is separate from fulfilment status; status updates and cancellation never change it. Older orders without payment fields show "Not recorded".
- **No payment gateway is configured.** Nothing is charged, no card numbers, CVV or UPI PINs are requested or stored, and no order is ever marked Paid. To add a real gateway later, create the order as `PENDING` and set `PAID` only from a server-verified gateway confirmation (webhook), never from the browser.
- Admin sees payment method and status in each order row, the order details and the CSV export; customers see them in My Orders and on the confirmation page.

## 14. Payment forms (v8)

- Methods: **UPI**, **Credit Card**, **Debit Card** (under Online Payment) and **Cash on Delivery**; stored as `UPI`, `CREDIT_CARD`, `DEBIT_CARD`, `COD`. Older `CARD` orders still display ("Credit/Debit Card (older order)").
- UPI form: UPI ID/VPA only (never a PIN), format-validated. Only a masked handle (e.g. `te***@okaxis`) is stored with the order. Card form: cardholder name, card number (Luhn + length, auto-spaced), expiry month/year (not in the past), CVV (3 digits, 4 for Amex). Checks live in `src/services/paymentValidation.js` and are unit-tested.
- Buttons: `Proceed to Pay` for UPI/Credit/Debit, `Place Order` for COD.
- **Simulation mode: no payment gateway is configured.** After a valid form, "Proceed to Pay" runs a short simulated hand-off and creates the order with `paymentStatus: PENDING` and `paymentMode: simulation`. It is never marked Paid, and the confirmation and admin views say it was simulated. Card numbers, CVV and expiry exist only in component memory while the form is open, are cleared on completion or when switching method, and are never saved, logged or sent anywhere. Use test data only.
- To go live: use the gateway's hosted checkout / secure card component (so card data never touches this app), create the order as `PENDING`, and set `PAID` only from a server-verified gateway confirmation.

## 15. Known limitations

No backend (see section 9). The 3D models were checked for valid geometry and silhouette with a software preview but not in a real browser/GPU. Responsive layouts, contrast and screen-reader behaviour were not audited in real browsers. Product specifications, materials and prices are concepts. No password reset, no online payments.
